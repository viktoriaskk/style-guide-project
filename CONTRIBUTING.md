# Участие в проекте

## Как предложить изменение

1. Опишите проблему и затронутую аудиторию в Issue или в описании PR.
2. Обновите локальную ветку `main` и создайте ветку с понятным именем.
3. Измените правило и связанные примеры. Не редактируйте собранный каталог `site/`.
4. Выполните проверки и изучите страницу в браузере.
5. Сделайте коммит, отправьте ветку и откройте Pull Request в `main`.
6. Получите ревью, внесите исправления отдельным коммитом и дождитесь одобрения.
7. После успешных проверок выполните merge и проверьте опубликованную страницу.

Владелец или участник с правом записи использует ветку в репозитории.
Внешний участник без права записи создаёт fork и открывает PR из него.
Рецензенту достаточно открыть PR; для формального одобрения, учитываемого защитой ветки,
может потребоваться доступ к репозиторию согласно его настройкам.

## Локальная установка

Требуются Git, Python 3.12 и Node.js 24 с npm. Из корня проекта:

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
npm ci
```

В PowerShell активируйте окружение командой `.venv\Scripts\Activate.ps1`.
Команда `npm ci` использует зафиксированные версии из `package-lock.json`.
Не добавляйте `.venv/` и `node_modules/` в Git.

## Проверка и сборка

```bash
npm run lint
python scripts/check_docs.py
python -m unittest discover -s tests -v
python -m mkdocs build --strict
python -m mkdocs serve
```

MkDocs напечатает локальный адрес. Проверьте навигацию, ссылки и отображение таблиц.
Остановите сервер сочетанием Ctrl+C. Статическая сборка находится в `site/`.

`markdownlint-cli2` проверяет структуру Markdown, скрипт — терминологию и обязательные
разделы инструкций, MkDocs — сборку и внутренние ссылки. Внешние сайты и смысл текста
проверяются отдельно. Сырые HTML-фрагменты разрешены только с обоснованием в PR.

## Conventional Commits

Формат: `тип(область): краткое описание`. Область необязательна.
Используйте `docs` для текста, `fix` для исправления дефекта,
`ci` для workflow, `test` для проверок и `chore` для обслуживания.
Описание должно объяснять изменение; произвольные сообщения вроде `update` не подходят.

```text
docs(guide): add text accessibility rules
fix(examples): clarify Moscow time before booking
ci(pages): deploy only after successful checks
```

## Как добавить раздел

1. Создайте ветку, например `docs/text-accessibility`.
2. Добавьте Markdown-файл в `docs/guide/` с одним H1.
3. Добавьте правила с уникальными кодами, примерами и критериями проверки.
4. Укажите файл в `nav` внутри `mkdocs.yml`.
5. Обновите связанные примеры и чек-лист, если меняются требования к ним.
6. Выполните проверки и откройте PR.

## Процесс ревью

Автор указывает цель, изменённые файлы и результаты проверок.
Рецензент проверяет факты, применимость правил и понятность примеров.
Комментарий содержит место, проблему и предложение либо вопрос.
Не оставляйте три одинаковых замечания ради количества.

Для лабораторной требуется минимум три содержательных комментария к PR партнёра.
Полученное ревью собственного PR не заменяет исходящие комментарии к чужому PR.
Если замечание принято, автор исправляет текст отдельным коммитом и отвечает в обсуждении.
После изменений рецензент повторно проверяет PR и одобряет его со своего аккаунта.
Самоодобрение автора не считается внешним ревью.

## CI/CD и завершение

Workflow `Docs` запускается на push, pull_request и вручную.
Job `quality` выполняет линтинг, проверки и строгую сборку.
Публикация выполняется только из `main`, только после успешного `quality`.
PR из внешней ветки не получает права публикации.

В GitHub включите **Settings → Pages → Source → GitHub Actions**.
После merge найдите успешный запуск workflow и откройте сайт по адресу из deployment.
Убедитесь, что новый раздел есть в навигации и его текст соответствует коммиту.
Сохраните ссылки на PR, комментарии, одобрение и запуск в `evidence/status.json`.
Не заменяйте реальные ссылки вымышленными.
