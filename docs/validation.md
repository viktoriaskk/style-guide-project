# Проверка стайлгайда

## Метод

Проверка выполнена на двух инструкциях: записи студента и публикации расписания преподавателя.
Для сравнения созданы два коротких учебных черновика в `evidence/drafts/`.
После проверки черновиков подготовлены полные инструкции по правилам руководства.

Метод включает автоматическую проверку и редакционный проход по сценариям.
Это проверка документации по согласованной модели, а не испытание работающего сервиса
и не пользовательское исследование. Внешнее ревью партнёров проводится отдельно через PR.

## Обнаруженные проблемы и решения

| Материал | Проблема черновика | Правило и исправление |
| --- | --- | --- |
| Студент | «Аккаунт» и «слот» вместо согласованных терминов | SG-10: «учётная запись» и «интервал» |
| Студент | Кнопка описана цветом и расположением | SG-07: точное название **Записаться** |
| Студент | Обещано письмо без основания в модели | SG-08: подтверждение проверяется в **Моих записях** |
| Студент | Не объяснены последствия отмены | SG-13 и SG-28: предупреждение перед подтверждением |
| Преподаватель | Не указан часовой пояс и конец интервала | SG-25: UTC+3, 30 минут и пример 14:00–14:30 |
| Преподаватель | Предложено удалить занятый интервал | SG-01: отмена консультации с причиной и проверкой последствий |
| Оба | Нет условий, наблюдаемого результата и ошибок | SG-12–SG-15: добавлены обязательные разделы |

## Уточнения правил после применения

При работе с двумя ролями понадобилось различать отмену записи студентом
и отмену консультации преподавателем. В словарь добавлены отдельные определения,
а в примерах описаны разные последствия.

Указания только формата времени оказалось недостаточно. Правило SG-25 требует
называть часовой пояс до выбора времени. Для сетевого сбоя правило SG-15 уточняет:
перед повтором операции нужно проверить список, поскольку результат запроса может быть неизвестен.

## Редакционная проверка примеров

| Критерий | Инструкция студента | Инструкция преподавателя |
| --- | --- | --- |
| Роль и условия указаны | Да | Да |
| Часовой пояс указан до действий | Да | Да |
| Названия элементов соответствуют модели | Да | Да |
| Шаги ведут к наблюдаемому результату | Да | Да |
| Отмена объяснена до подтверждения | Да | Да |
| Ошибки имеют следующий шаг | Да | Да |
| Нет обещания обязательного письма | Да | Да |

Для студента проверены сценарии успешной записи, занятого интервала, отмены до начала
и неопределённого результата при сетевой ошибке. Для преподавателя — создание интервала,
пересечение времени, отмена занятого интервала и неопределённое сохранение.
Все сценарии сопоставлены с моделью продукта без запуска самого сервиса.

## Автоматическая проверка

Команды и фактические результаты сохраняются в каталоге `evidence/` репозитория.
Проверка черновиков должна завершаться с ошибкой; это контроль обнаружения дефектов.
Проверка готовых инструкций должна завершаться успешно.

```bash
python scripts/check_docs.py evidence/drafts/student-before.md evidence/drafts/teacher-before.md
python scripts/check_docs.py
npm run lint
python -m unittest discover -s tests -v
python -m mkdocs build --strict
```

## Оценка качества

Руководство позволяет описать обе роли с едиными терминами и проверяемыми результатами.
Примеры показали необходимость правил о часовом поясе, различии отмен и повторе запроса.
Автоматизация обнаруживает часть ошибок раньше ревью, но не доказывает удобство инструкции
для реальных пользователей. Следующий этап — независимая проверка партнёрами и исправления
по их замечаниям. Протокол не утверждает, что это ревью уже получено.
